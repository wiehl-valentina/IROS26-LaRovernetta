Mejoras de Ingeniería para La Rovernetta

Este documento detalla el plan de mejoras de ingeniería que nuestro equipo debe implementar en el código de autonomía, visión y control. Todas las propuestas respetan estrictamente la regla del desafío: el SDK oficial no se modifica; nuestro trabajo es construir un cliente inteligente, seguro y altamente modular que consuma el SDK para guiar al robot hacia sus objetivos.

📝 Bloc de Notas Interactivo del Lector 0 Notas Escritas
📌 Principio de Diseño Fundamental: El SDK provisto (servidor FastAPI y WebRTC) actúa como una caja negra de hardware que expone puntos de enlace HTTP (/api/status y /api/send-command). El 100% de las mejoras detalladas a continuación se aplican en el lado del cliente de autonomía (procesamiento concurrente, supervisión de seguridad, gestión de memoria GPU, cinemática y pruebas automatizadas).
01

Adaptador Asíncrono de Alto Rendimiento para el SDK (Async SDK Adapter)

Concurrencia & Desacoplamiento
⚠️ Limitación Actual en el Cliente
El script sdk_client.py realiza consultas HTTP síncronas bloqueantes (requests.get) en el mismo hilo de ejecución donde corren las redes neuronales y el planificador. Si la conexión local sufre un retardo de 35 ms, todo el lazo de visión y cálculo de trayectoria se congela.
✅ Solución de Ingeniería en el Cliente
Diseñar un Adaptador de Cliente Asíncrono con un hilo de fondo dedicado (usando httpx.AsyncClient o aiohttp) que mantenga una cola circular de tamaño 1 (latest-only ring buffer). La percepción lee de inmediato el fotograma más reciente en memoria sin esperar a la red.
Pasos de Implementación Recomendados:
Paso 1
Crear la clase AsyncRoverClient que ejecuta un bucle de eventos independiente para consultar continuamente /api/status a la frecuencia óptima de la cámara (15 Hz).
Paso 2
Desacoplar la descodificación de imágenes JPEG/Base64 a tensores de OpenCV en un pool de subprocesos ligeros para no saturar el hilo principal de Python.
Paso 3
Permitir que el planificador de trayectorias consulte instantáneamente la última pose GPS y el fotograma listo en memoria compartida con latencia cercana a 0 ms.

02

Supervisor de Seguridad y Temporizador Watchdog del Lado Cliente

Tolerancia a Fallos
⚠️ Riesgo Actual en el Software
Si la inferencia del modelo SAM-TP o YOLO sufre una excepción no capturada, una fuga de memoria VRAM o un cuelgue de CUDA, el cliente deja de emitir órdenes. Dado que el SDK simplemente ejecuta la última orden recibida, el robot continuará desplazándose sin control.
✅ Solución de Ingeniería en el Cliente
Implementar un Supervisor Guardián de Seguridad (Safety Watchdog) en un hilo de máxima prioridad. Si el lazo de percepción o navegación no produce un comando válido en menos de 250 ms, el guardián despacha de inmediato {"linear": 0.0, "angular": 0.0} al SDK para frenar el vehículo.
Mecanismos de Protección a Incorporar:
1
Interruptor de Hombre Muerto (*Deadman Switch*): Hilo temporizado que anula la velocidad en el SDK si expira el tiempo de latido (*heartbeat*) del pipeline de visión.
2
Detección de Atascamiento por Odometría: Si el controlador envía velocidad de avance ($v > 0.2$ m/s) pero la odometría visual VIO reporta velocidad nula durante más de 1.5 segundos, se interrumpe la navegación y se activa una rutina de desatasco en reversa.
3
Filtro de Aceleración (*Slew-Rate Limiter*): Suaviza los comandos enviados al SDK para proteger la tracción y evitar patinamiento en curvas bruscas.

03

Contenerización y Entorno de Desarrollo Determinista para la Autonomía

Reproducibilidad
⚠️ Dificultad Actual de Instalación
Los modelos de visión y planificación requieren librerías complejas (PyTorch con CUDA 12.6, Torchvision, SAM-2, Ultralytics) que generan conflictos de compilación en Windows y obligan a mantener dos entornos virtuales manuales y frágiles.
✅ Solución de Ingeniería en el Cliente
Empaquetar todo el stack de autonomía en una imagen de Docker con soporte NVIDIA Container Toolkit gestionada mediante uv y un archivo uv.lock determinista. El contenedor de autonomía interactúa con el servidor SDK a través de la red local HTTP estándar.
# Estructura del entorno de autonomía reproducible FROM nvidia/cuda:12.6.0-runtime-ubuntu22.04 AS autonomy_engine WORKDIR /app RUN apt-get update && apt-get install -y python3-pip libgl1-mesa-glx ffmpeg git COPY pyproject.toml uv.lock ./ RUN pip install --no-cache-dir uv && uv sync --frozen COPY genie/ ./genie/ COPY traversability/ ./traversability/ CMD ["uv", "run", "python", "-m", "genie_rover.bridge", "--config", "configs/rover.yaml"]

04

Configuración Declarativa, Centralizada y Validada con Tipos

Cero Hardcoding
⚠️ Desorden de Parámetros en el Código
Los parámetros críticos del robot (límites de velocidad, pesos de costes en el planificador polinomial, resolución de la cuadrícula BEV y umbrales de confianza de YOLO) están dispersos en archivos YAML, variables de entorno y constantes numéricas fijas en el código.
✅ Solución de Ingeniería en el Cliente
Implementar un modelo de configuración unificado con Pydantic Settings. Todos los parámetros se validan al arrancar la aplicación: si un valor viola las restricciones físicas (ej. velocidad lineal negativa o mayor a 0.5 m/s), el sistema alerta de inmediato y evita iniciar la marcha.
# Modelo de configuración robusto con validaciones físicas en Pydantic from pydantic import BaseModel, Field class AutonomyConfig(BaseModel): sdk_base_url: str = Field(default="http://localhost:8000", description="URL del servidor SDK") max_linear_speed: float = Field(default=0.40, ge=0.0, le=0.60, description="Velocidad máxima (m/s)") max_angular_speed: float = Field(default=1.10, ge=0.0, le=2.00, description="Velocidad de giro (rad/s)") yolo_confidence_threshold: float = Field(default=0.65, ge=0.1, le=1.0, description="Filtro de confianza para el cono") bev_grid_resolution_meters: float = Field(default=0.05, gt=0.0, description="Tamaño de celda BEV")

05

Simulación Mediante Mock del SDK y Pruebas Automatizadas (CI/CD)

Calidad de Software
⚠️ Dependencia Exclusiva del Robot Real
Cualquier cambio en el planificador o en los pesos del modelo de percepción requiere encender el robot físico o conectarse al rover remoto. No existen pruebas de integración automáticas en el repositorio que certifiquen la estabilidad del código.
✅ Solución de Ingeniería en el Cliente
Construir un Mock Server del SDK que simula con fidelidad las respuestas de /api/status y acepta /api/send-command, inyectando secuencias de video pregrabadas y trayectorias GPS sintéticas. Esto permite ejecutar pruebas de regresión automáticas en GitHub Actions en cada Pull Request.
Estructura de Pruebas Automatizadas:
Nivel 1
Pruebas Unitarias de Algoritmos Puros: Verificación matemática del planificador polinomial, proyección de coordenadas ENU y transformaciones de perspectiva sin requerir GPU.
Nivel 2
Pruebas de Regresión de Visión con Datasets Grabados: Evaluación automática de SAM-TP y YOLO contra 40 imágenes de prueba etiquetadas, verificando que la precisión y la velocidad de inferencia se mantengan estables.
Nivel 3
Prueba de Integración End-to-End con Mock SDK: Simula una misión completa de 3 minutos validando que la máquina de estados transicione correctamente de navegación GPS a detección de cono.

06

Gestión Geométrica Mediante Árbol de Transformadas Cinemáticas (TF)

Geometría Espacial
⚠️ Cálculos Espaciales Manuales y Rígidos
Las proyecciones hacia la vista cenital (BEV) asumen alturas y ángulos de inclinación fijos codificados en scripts aislados. Si la cámara se recoloca físicamente en el chasis, se deben recalcular matrices manualmente en varios archivos.
✅ Solución de Ingeniería en el Cliente
Implementar un módulo cinemático formal en el cliente que mantenga el árbol de transformaciones continuas: $$\text{mapa (ENU)} \longrightarrow \text{odometría (VIO)} \longrightarrow \text{chasis (base\_link)} \longrightarrow \text{lente (camera\_link)}$$ Cualquier ajuste en la posición de la cámara se actualiza como una traslación tridimensional en un único archivo de configuración.

07

Observabilidad, Logging Estructurado y Diagnóstico en Tiempo Real

Monitoreo de Misión
⚠️ Dificultad para Diagnosticar Fallos en Campo
El código utiliza instrucciones print() dispersas en consola sin marcas de tiempo estándar, niveles de advertencia ni guardado estructurado, dificultando reconstruir la causa raíz de un fallo o una desviación de ruta tras una prueba.
✅ Solución de Ingeniería en el Cliente
Adoptar Logging Estructurado en JSON (usando loguru o structlog) con rotación automática de archivos por sesión de prueba. Registrar métricas clave en cada ciclo: tiempo de inferencia GPU en ms, tasa de cuadros por segundo (FPS), latencia de red con el SDK y covarianza de la odometría.

08

Hoja de Ruta de Implementación Práctica (Roadmap)

Plan Secuencial

Para no interrumpir los ensayos de navegación activa, estas mejoras se dividen en 3 etapas secuenciales de desarrollo:

Fase 1 • Inmediata
Seguridad y Configuración
• Watchdog en cliente con corte de motor por timeout.
• Esquema de configuración tipado con Pydantic.
• Logging estructurado en JSON con timestamps.
• Filtro de suavizado de aceleración (slew-rate).
Fase 2 • Corto Plazo
Contenedores y Mock SDK
• Contenedor Docker para el stack de autonomía con CUDA.
• Servidor Mock del SDK para pruebas unitarias sin rover.
• Pipeline de CI/CD automatizado en GitHub Actions.
• Módulo de cinemática y árbol de transformadas TF.
Fase 3 • Mediano Plazo
Concurrencia y Optimización
• Adaptador de cliente HTTP asíncrono con buffer circular.
• Optimización de inferencia de modelos con TensorRT / ONNX.
• Grabación determinista de telemetría de misiones.
• Panel web de telemetría y diagnósticos en tiempo real.
