Cómo el rover decide
por dónde manejar

Cada 0.5 segundos el rover mira un frame de cámara, lo convierte en un mapa de "dónde se puede pisar", lo divide en corredores verticales y elige el más seguro y más cercano al rumbo del próximo checkpoint. Sin mapas previos, sin memoria de largo plazo: percibe, decide y manda un comando — una y otra vez.

01 · Estructura general

El ciclo de la Demo Mission

La misión completa (MissionRunner.run() en mission.py) es un loop que se repite hasta llegar al último checkpoint. Cada iteración pasa por siete etapas. Tocá cada tarjeta para ver qué recibe, qué procesa, qué produce y cómo afecta a la siguiente etapa.

02 · Percepción del terreno

02De un frame a una máscara de transitabilidad

El modelo (SAM-TP, SAM 2.1 con un prompt de transitabilidad aprendido, afinado con ~50.000 frames del Mini+) convierte el frame en una máscara HxW con valores entre 0 y 1: 1 = transitable 0 = bloqueado. No hay puntos de prompt reales — la API de SAM2 exige alguno, pero el encoder de SAM-TP los ignora por completo.

1. Decodificar cualquier payload — images.py

El SDK entrega el frame como base64 sin prefijo, y el formato real (PNG o JPEG) depende de una variable de entorno del servidor, no de lo que el cliente espera. Por eso to_rgb() nunca confía en la extensión declarada: lee los magic bytes del archivo para reconocer PNG/JPEG/WEBP/GIF/BMP antes de decodificar. Acepta además arrays numpy, imágenes PIL, rutas de archivo y data: URIs, todo por el mismo punto de entrada.

# images.py — sniff_format() def sniff_format(data: bytes) -> str | None: for magic, name in _MAGIC_SIGNATURES: if data[:len(magic)] == magic: return name # "png", "jpeg", ...

2. Inferencia — predictor.py

TraversabilityPredictor.predict() corre SAM-TP una vez sobre el frame y aplica sigmoid a los logits crudos para obtener la máscara en [0,1]. El modelo se construye una sola vez por proceso (una construcción por llamada agrega latencia real) y se reutiliza en cada frame.

# predictor.py logits = masks[0] # salida cruda del modelo mask = _sigmoid(logits) # -> HxW float32 en [0,1] mask = refine_traversability_by_contrast(mask, rgb)

3. Refinamiento por contraste — el punto ciego del modelo

SAM-TP fue entrenado como "piso vs. no-piso", así que puede etiquetar como transitable un objeto oscuro parado sobre piso claro (otro rover, una silla, un obstáculo bajo). refine_traversability_by_contrast() corrige esto sin reentrenar nada: toma los píxeles que el modelo ya marcó como transitables, calcula su luminancia mediana (referencia de "cómo se ve el piso" en ese frame) y degrada a bloqueado cualquier píxel "transitable" que sea mucho más oscuro que esa referencia (lum < mediana × darkness_ratio, default 0.65). La referencia se recalcula cada frame, así que se adapta a la luz del momento.

píxel de referencia (piso, transitable) degradado a bloqueado por ser mucho más oscuro que el piso
03 · Manejo de obstáculos

03Detección y evasión de obstáculos

No hay un "detector de obstáculos" separado: un obstáculo es, para el sistema, cualquier región de la máscara con valor por debajo de drivable_thresh (0.5). Todo lo demás — parar, girar, elegir otro corredor — es una consecuencia de cómo se agregan esos valores en policy.py.

Estructura del código que interviene

ArchivoResponsabilidad frente a obstáculos
predictor.pyGenera el valor por píxel (0–1) y corrige obstáculos oscuros mal etiquetados (contraste).
policy.pyDecide si un obstáculo bloquea el avance: recorta la región de interés (ROI), calcula el test de parada por fracción y descarta corredores pobres.
mission.pySi ni girando hay salida visible, dispara un giro de arco hacia el objetivo en vez de quedarse esperando.
client.pyConvierte la decisión de "parar" en un comando activo {0,0} — nunca en silencio.

Cómo se detecta un obstáculo a nivel código

# policy.py — suggest_command() roi # recorte inferior de la máscara: solo el piso cercano al rover roi = m[int(cfg.roi_top * h):, :] # roi_top=0.55 -> ignora el 55% superior (cielo/horizonte) # cada columna recibe un peso mayor si está más cerca del rover (fila inferior) row_w = np.linspace(1.0, cfg.bottom_weight, roi.shape[0])[:, None] col_score = (roi * row_w).sum(axis=0) / row_w.sum() # test de parada: NO es "¿hay algún píxel bloqueado?" — eso pararía siempre center_band = roi[:, bounds[center_idx]:bounds[center_idx+1]] center_blocked_frac = (center_band < cfg.drivable_thresh).mean() center_open = center_blocked_frac < cfg.stop_center_fraction # default: 40%

Este diseño es deliberado: la salida real del modelo siempre tiene algo de ruido (algunos píxeles bloqueados sueltos), así que un test "cualquier píxel bloqueado = parar" frenaría al rover en cada frame. El test es por fracción del corredor central: recién se considera bloqueado si el 40% o más de esa banda está por debajo del umbral.

Si ningún corredor lateral supera min_corridor_score, la decisión es reason="blocked": linear=0, angular=0. El rover no "adivina" ni promedia hacia el obstáculo — se detiene activamente.

Cómo el rover evita elegir caminos peligrosos

  • El objetivo (steering target) nunca es el centro de toda la imagen

    Es el centroide ponderado dentro del corredor elegido. Esto importa especialmente en una máscara bimodal (dos aberturas, pared en el medio): si el objetivo fuera el centro de la vista completa, el rover apuntaría exactamente a la pared entre las dos aberturas. Apuntando al centroide del corredor ganador, apunta dentro de la abertura real.

  • Un corredor "algo" transitable no alcanza

    min_corridor_score (0.35) es un piso de calidad: un corredor con score apenas positivo no se considera "viable" solo porque técnicamente no es cero.

  • El sesgo hacia el objetivo nunca vence a la seguridad

    El bias GPS multiplica los scores de transitabilidad, no los reemplaza. Si el objetivo está a la derecha pero solo el corredor izquierdo es transitable, el rover sigue yendo a la izquierda — el bias apenas desempata entre corredores igualmente seguros.

  • El rover nunca "confía" en el último comando

    El SDK repite el último comando para siempre hasta recibir uno nuevo. Por eso "no enviar nada" nunca es una forma válida de parar: cada decisión de parada manda activamente {linear:0, angular:0}, con reintentos en client.stop().

Cómo se actualiza la información cuando el rover avanza

No hay memoria de obstáculos entre frames: cada iteración recalcula todo desde cero a partir del frame nuevo. Es una política reactiva y sin estado (salvo dos excepciones con estado propio: el HeadingEstimator, que recuerda el último rumbo GPS válido, y la posición/checkpoint actual de la misión). Esto es intencional: un obstáculo que ya no está en cámara deja de influir en la decisión inmediatamente, sin necesidad de "olvidarlo" explícitamente.

04 · Manejo de corredores

04Qué es un corredor y cómo se elige

Un corredor es una banda vertical de la imagen (por defecto la máscara se divide en num_corridors = 9 bandas iguales, siempre un número impar para que exista un corredor central exacto). Cada corredor tiene un score entre 0 y 1: el promedio ponderado de la máscara en esa banda, dando más peso a las filas cercanas al rover (bottom_weight).

Cómo se detecta un corredor

No hay una detección explícita de "esto es un corredor": los 9 corredores siempre existen, en posiciones fijas. Lo que varía frame a frame es su score. Un corredor "aparece" simplemente cuando su score supera min_corridor_score (0.35) — no es un objeto detectado, es un umbral cruzado.

Cómo se determina su dirección

Cada corredor tiene una posición fija en x. La dirección de giro sale de comparar la posición del corredor elegido contra el centro de la imagen: si el centroide cae a la derecha del centro, el ángulo resultante es negativo (giro a la derecha); si cae a la izquierda, positivo (convención del SDK: angular positivo = izquierda).

# policy.py — selección del mejor corredor order = np.argsort(-biased) # ordena corredores por score (con sesgo de objetivo) best = min(empatados_en_el_maximo, key=lambda i: abs(i - center_idx)) # empate -> el más cercano al centro # el objetivo de giro es el centroide DENTRO del corredor, no del frame band_cols = col_score[bounds[best]:bounds[best+1]] target_x = (xs * band_cols).sum() / band_cols.sum()

Obstáculo dentro del corredor elegido

El score de esa banda baja proporcionalmente a cuánta superficie bloqueada contiene. Si cae por debajo de min_corridor_score, ese corredor deja de ser candidato en el siguiente frame — no hay "expulsión" explícita, simplemente pierde el umbral.

Selección de corredor alternativo

Se recalculan los 9 scores y se vuelve a tomar el máximo (con sesgo de objetivo si hay checkpoint activo). No hay "segundo mejor guardado" de frames anteriores: la alternativa sale de la misma pasada de este frame.

Cuándo se abandona un corredor

Se "abandona" en el instante en que, en un nuevo frame, ya no es el de mayor score sesgado, o su score cae debajo de 0.35. No hay histéresis: el sistema es puramente reactivo a lo que ve ahora.

Sesgo hacia el objetivo GPS (goal bias)

Cuando hay un checkpoint activo, mission.py calcula el rumbo hacia él con gps_bearing_and_distance() y lo compara contra el heading actual del rover (estimado por GPS course-over-ground, ver más abajo) para obtener goal_offset_deg. La política proyecta ese ángulo a una posición x de imagen con un modelo pinhole simple y multiplica los scores de cada corredor por una campana gaussiana centrada en esa posición:

# policy.py — _goal_offset_to_image_x + bias gaussiano gx = tan(rad(goal_offset_deg)) / tan(rad(hfov_deg/2)) # bearing -> x normalizado [-1,1] gauss = exp(-0.5 * ((centros_x - gx) / goal_sigma)**2) biased = corridor_scores * (goal_bias_floor + (1-goal_bias_floor) * gauss)

goal_bias_floor (0.2) asegura que ningún corredor quede en cero solo por estar lejos del objetivo — la transitabilidad sigue dominando, el objetivo solo desempata entre corredores igualmente seguros.

Cuando el objetivo está fuera de cámara: el giro de arco

Si |goal_offset_deg| > turn_in_place_deg (70°), el objetivo está demasiado a un costado o directamente detrás — la cámara no puede verlo, así que no tiene sentido buscar corredores. MissionRunner._decide() evita ese caso con un giro de arco en vez de una rotación en el lugar:

# mission.py — arc_turn_to_goal if abs(goal_offset_deg) > self.turn_in_place_deg: turn = -max_angular if goal_offset_deg > 0 else max_angular return CommandDecision(linear=self.arc_turn_linear, angular=turn, stop=False, reason="arc_turn_to_goal")

La razón de usar un arco (linear>0) y no un giro puro es que el heading del rover se estima por GPS course-over-ground: un rover que gira en el lugar no se desplaza, y sin desplazamiento el estimador de rumbo no tiene señal nueva (ver sección de percepción de rumbo abajo). Un arco mantiene el heading actualizándose mientras gira.

Cómo se "vuelve a encontrar" un corredor después de perderlo

No hay una rutina de "recuperación de corredor" separada: al no tener memoria de corredores entre frames, simplemente el siguiente frame vuelve a intentar encontrar el mejor de los 9. Si en ese frame ninguno alcanza el umbral, la decisión es blocked (parar) y se reintenta en el frame siguiente — el rover se queda detenido hasta que algún corredor vuelva a ser viable (por ejemplo, porque el obstáculo salió de cuadro o el propio giro cambió la vista).

06 · Lógica principal, explicada simple

06El razonamiento completo, en lenguaje natural

Pseudocódigo — un paso de misión

cada 0.5s, para el checkpoint activo: leer telemetría (lat, lon, velocidad, brújula) heading = estimar_rumbo_por_gps(telemetría) # o brújula si aún no hubo movimiento si hay posición GPS: bearing_al_checkpoint = calcular_rumbo(pos_actual, checkpoint) goal_offset = bearing_al_checkpoint - heading si distancia_al_checkpoint <= 8m: intentar POST /checkpoint-reached # el backend valida el radio real; si rechaza, seguir manejando si |goal_offset| > 70°: comando = arco_hacia_el_objetivo() # objetivo fuera de cámara si no: máscara = SAM_TP(frame_cámara) comando = elegir_corredor(máscara, goal_offset) enviar comando (o parar activamente si stop=true)

Pseudocódigo — elegir_corredor()

recortar la parte inferior de la máscara (roi_top) dividir en 9 bandas verticales score[i] = promedio ponderado (más peso a filas cercanas) si corredor_central mayormente bloqueado (≥40%): si ningún corredor supera 0.35 de score: devolver STOP si no: girar en el lugar hacia el mejor lateral si no (el centro está abierto): aplicar sesgo gaussiano hacia goal_offset a cada score elegir el corredor con mayor score sesgado apuntar al centroide DENTRO de ese corredor (no al centro del frame) linear = velocidad_min + (velocidad_max - velocidad_min) * score_del_centro devolver {linear, angular}
